数字电路综合入门
================


本章简要介绍数字电路综合的基本原理。

抽象层次
--------


数字电路可以用不同的抽象层次表示。在设计过程中，通常首先用较高层次的
抽象来描述电路。实现则可以理解为在较低抽象层次上找到功能等价的表示。
当这一过程由软件自动完成时，就称为综合。

因此，综合就是把电路的高级表示自动转换为功能等价的低级表示。
:numref:`图 %s <fig:Basics_abstractions>` 列出了不同的抽象层次，以及它们
与各类综合的关系。

.. figure:: /_images/primer/basics_abstractions.svg
	:class: width-helper invert-helper
	:name: fig:Basics_abstractions

	不同的抽象层次与综合。

无论电路的低层表示是如何获得的（通过综合还是手工设计），通常都会通过比较
低层表示与高层表示的仿真结果来验证低层表示 [1]_。因此，即使不使用综合，
也必须在所有层次上都有电路的可仿真表示，以便验证设计。

注意：诸如“High-Level”这类术语的确切含义当然不是一成不变的。例如 HDL
“ABEL”于 1985 年首次提出时被称为“A High-Level Design Language for
Programmable Logic Devices” :cite:p:`ABEL`，但在今天它不会被当作一种
“High-Level Language”。

系统级
~~~~~~


系统的系统级抽象只关注其最大的构建模块，如 CPU 和计算核心。在这一层次上，
电路通常用 C/C++ 或 Matlab 等传统编程语言来描述。有时会使用专门用于
系统级电路仿真的软件库，例如 SystemC。

通常不使用综合工具把电路的系统级表示自动转换为更低层次的表示。但已有
系统级设计工具，可用于连接系统级构建模块。

IEEE 1685-2009 标准定义了 IP-XACT 文件格式，可用于表示系统级设计，以及
可用于此类系统级设计的构建模块。:cite:p:`IP-XACT`

高级
~~~~


系统的高级抽象（有时称为算法级）也常用传统编程语言表示，但只使用缩减后的
特性集。例如，用 C 语言在高级抽象层次上表示设计时，指针只能用于模仿硬件
中存在的概念，如存储器接口。不允许使用功能完整的动态内存管理，因为它在
数字电路中没有对应概念。

已有工具可以把高级代码（通常是以附带额外元数据的 C/C++/SystemC 代码形式）
综合为行为级 HDL 代码（通常以 Verilog 或 VHDL 代码形式）。除了众多商业
高级综合工具外，还有一些 FOSS 高级综合工具。

行为级
~~~~~~


在行为级抽象层次上，使用 Verilog 或 VHDL 等面向硬件描述的语言来描述电路，
但至少在电路描述的一部分中会使用所谓的行为级建模。在行为级建模中，语言
必须提供某种特性，允许用命令式编程来描述数据路径和寄存器。在 Verilog 中
这就是 always 块，在 VHDL 中则是过程块（process block）。

在行为级建模中，代码片段与敏感列表一起给出；敏感列表是一组信号和条件。
在仿真中，只要敏感列表中的某个信号值发生变化，或某个条件被触发，就会执行
该代码片段。综合工具必须能够把这种表示转换为合适的数据路径，再后接合适
类型的寄存器。

例如，考虑下面的 Verilog 代码片段：

.. code:: verilog
   :number-lines:

   always @(posedge clk)
       y <= a + b;

在仿真中，只要检测到信号 ``clk`` 的上升沿，就会执行语句 ``y <= a + b``。
然而综合结果会包含一个始终计算和 ``a + b`` 的加法器，其后接一个 D 型
触发器，加法器的输出连接到其 D 输入端，信号 ``y`` 位于其 Q 输出端。

通常，行为级建模中使用的命令式代码片段可以包含条件执行语句（Verilog 中的
``if`` 和 ``case`` 语句）以及循环，只要这些循环可以完全展开。

有趣的是，除了 Yosys 之外，似乎没有其他能够执行 Verilog 或 VHDL 行为级
综合的 FOSS 工具。

寄存器传输级（RTL）
~~~~~~~~~~~~~~~~~~~


在寄存器传输级，设计由组合数据路径和寄存器（通常是 D 型触发器）表示。
下面的 Verilog 代码片段与前面的 Verilog 示例等价，但采用 RTL 表示：

.. code:: verilog
   :number-lines:

   assign tmp = a + b;       // combinatorial data path

   always @(posedge clk)     // register
       y <= tmp;

采用 RTL 表示的设计通常用 Verilog 和 VHDL 等 HDL 存储。但只使用非常有限
的一部分特性，即用于建模所用寄存器类型的最简 always 块（Verilog）或
过程块（VHDL），以及用于数据路径逻辑的无条件赋值。在这一层次上使用
HDL 可以简化仿真，因为仿真 RTL 表示的设计不需要额外工具。

许多优化和分析在 RTL 层次上执行效果最好。例如有限状态机（FSM）检测与
优化、识别存储器或其他较大的构建模块，以及识别可共享资源。

注意，RTL 是第一个把电路表示为电路元件（寄存器和组合单元）与信号构成的图
的抽象层次。这种图在以单元和连接列表的形式编码时，称为网表。

RTL 综合很容易，因为网表中的每个电路节点元件都可以简单地替换为等价的门级
电路。然而，RTL 综合这一术语通常不仅指把 RTL 网表综合为门级网表，还指在
RTL 表示内执行一系列高度复杂的优化，例如上面列出的例子。

已有一些 FOSS 工具可以在 RTL 综合步骤的范畴内执行孤立的任务。但似乎没有
哪个 FOSS 工具能覆盖广泛的 RTL 综合操作。

逻辑门级
~~~~~~~~


在逻辑门级，设计由只使用少量单比特单元的网表表示，例如基本逻辑门（AND、
OR、NOT、XOR 等）和寄存器（通常是 D 型触发器）。

这一层次上可以使用多种网表格式，例如电子设计交换格式（EDIF），但为了便于
仿真，通常使用 HDL 网表。后者是一个 HDL 文件（Verilog 或 VHDL），只使用
最基本的语言结构来实例化和连接单元。

逻辑综合有两个挑战：第一是在门级网表中寻找优化机会，第二是把逻辑门网表
最优地（或至少较好地）映射为物理可用门类型的等价网表。

最简单的逻辑综合方法是两级逻辑综合，即把逻辑函数转换为积之和表示，例如
使用卡诺图。这种方法很简单，但最坏情况下开销呈指数增长，并且无法高效利用
AND/NAND、OR/NOR 和 NOT 门之外的物理门。

因此现代逻辑综合工具会使用复杂得多的多级逻辑综合算法
:cite:p:`MultiLevelLogicSynth`。这些算法大多把逻辑函数转换为二叉决策图
（BDD）或与反相图（AIG），并基于该表示进行处理。前者的优点是具有唯一的
规范形式。后者的最坏情况性能好得多，因此更适合综合大型逻辑函数。

多级逻辑综合已有优秀的 FOSS 工具。

Yosys 包含基本的逻辑综合功能，但也可以使用 ABC 完成逻辑综合步骤。推荐
使用 ABC。

物理门级
~~~~~~~~


在物理门级，只使用目标架构上物理可用的门。有些情况下这可能只有 NAND、NOR
和 NOT 门以及 D 型寄存器。另一些情况下可能包含比逻辑门级所用单元更复杂的
单元（例如完整的半加器）。对于基于 FPGA 的设计，物理门级表示是带可选输出
寄存器的 LUT 网表，因为它们是 FPGA 逻辑单元的基本构建模块。

对综合工具链来说，这一抽象通常是最低层次。对于基于 ASIC 的设计，单元库
可能包含更多关于物理单元如何映射到单个开关（晶体管）的信息。

开关级
~~~~~~


电路的开关级表示是把单个晶体管用作单元的网表。Verilog 和 VHDL 都可以进行
开关级建模，但在现代设计中很少使用，因为在现代数字 ASIC 或 FPGA 流程中，
物理门被视为逻辑电路的原子构建模块。

Yosys
~~~~~


Yosys 是一个 Verilog HDL 综合工具。这意味着它以行为级设计描述为输入，并
生成该设计的 RTL、逻辑门级或物理门级描述作为输出。Yosys 的主要优势是
行为级综合和 RTL 综合。Yosys 中有大量命令（综合 pass，即处理流程），可
用于在行为级、RTL 和逻辑综合范畴内执行各种综合任务。Yosys 被设计为
可扩展的，因此是实现面向特定任务的自定义综合工具的良好基础。

可综合 Verilog 的特性
---------------------


Verilog :cite:p:`Verilog2005` 中可综合的子集在单独的 IEEE 标准文档
IEEE 标准 1364.1-2002 :cite:p:`VerilogSynth` 中规定。该标准还描述了某些
语言结构在综合语境下应如何解释。

本节按复杂度递增的顺序，简要概述可综合 Verilog 最重要的特性。

结构化 Verilog
~~~~~~~~~~~~~~


结构化 Verilog（也称为 Verilog 网表）是用 Verilog 语法书写的网表。这种
情况下只使用以下语言结构：

-  常量值
-  wire 和端口声明
-  信号到其他信号的静态赋值
-  单元实例化

许多工具（尤其是综合链的后端）只支持结构化 Verilog 作为输入。ABC 就是
这样一个例子。遗憾的是，没有标准规定结构化 Verilog 究竟是什么，因此在
属性或多比特信号等特性方面，结构化 Verilog 支持哪些语法结构会带来一些
混乱。

Verilog 中的表达式
~~~~~~~~~~~~~~~~~~


在所有 Verilog 接受常量值或信号名的场合，也可以使用由算术运算（如
``+``、``-`` 和 ``*``）、布尔运算（如 ``&`` (AND)、``|`` (OR) 和
``^`` (XOR)）以及许多其他运算（比较运算、一元运算符等）构成的表达式。

在综合过程中，这些运算符会被实现相应功能的单元替换。

许多声称能够处理 Verilog 的 FOSS 工具实际上只支持基本的结构化 Verilog 和
简单表达式。可以用 Yosys 把功能完整的可综合 Verilog 转换为这个更简单的
子集，从而使这类应用能够使用更丰富的 Verilog 特性。

行为级建模
~~~~~~~~~~


使用 Verilog always 语句的代码采用行为级建模。在行为级建模中，电路通过
命令式程序代码描述，这些代码在某些事件发生时执行，即信号的任意变化、
上升沿或下降沿。这在仿真中是非常灵活的结构，但只有在建模以下情况之一时
才可综合：

-  | **异步或锁存逻辑**
   | 在这种情况下，敏感列表必须包含 always 块中使用的所有表达式。
     这些情况可以使用语法 ``@*``。此类示例如下：

   .. code:: verilog
      :number-lines:

      // asynchronous
      always @* begin
          if (add_mode)
              y <= a + b;
          else
              y <= a - b;
      end

      // latched
      always @* begin
          if (!hold)
              y <= a + b;
      end

   注意，锁存逻辑通常被认为是不良风格，很多情况下只是草率 HDL 设计的
   结果。因此，只要生成了锁存逻辑，许多综合工具都会发出警告。

-  | **同步逻辑（可选同步复位）**
   | 这是输出端带有 D 型触发器的逻辑。在这种情况下，敏感列表必须只包含
     相应的时钟沿。示例：

   .. code:: verilog
      :number-lines:

      // counter with synchronous reset
      always @(posedge clk) begin
          if (reset)
              y <= 0;
          else
              y <= y + 1;
      end

-  | **带异步复位的同步逻辑**
   | 这是输出端带有异步复位的 D 型触发器逻辑。在这种情况下，敏感列表必须
     只包含相应的时钟沿和复位沿。复位分支中赋的值必须是常量。示例：

   .. code:: verilog
      :number-lines:

      // counter with asynchronous reset
      always @(posedge clk, posedge reset) begin
          if (reset)
              y <= 0;
          else
              y <= y + 1;
      end

许多综合工具（包括 Yosys）支持可用 always 语句建模的更大触发器子集。
但 Verilog 综合标准只涵盖上面列出的那些情况，在编写新设计时应当把自己
限制在这些情况内。

在行为级建模中，可以使用阻塞赋值（=）和非阻塞赋值（<=）。阻塞赋值与非
阻塞赋值的概念是 Verilog 中最容易被误解的结构之一 :cite:p:`Cummings00`。

阻塞赋值的行为与任何命令式编程语言中的赋值完全相同，而在非阻塞赋值中，
赋值右侧会立即求值，但左侧寄存器的实际更新会推迟到时间步结束时。例如
Verilog 代码 ``a <= b; b <= a;`` 会交换两个寄存器的值。


函数和任务
~~~~~~~~~~


Verilog 支持函数和任务，用于把在多个地方使用的语句打包起来（类似于
命令式编程中的过程）。这两种结构都可以通过用函数或任务的主体替换函数/
任务调用来轻松实现。

条件语句、循环和 generate 语句
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~


Verilog 在 ``always`` 语句中支持 ``if-else`` 语句和 ``for`` 循环。

它还支持在模块级的 ``generate`` 语句中使用这两种特性。这可以用于根据模块
参数有选择地启用或禁用模块的一部分（``if-else``），或生成一组相似的
子电路（``for``）。

always 块内部的 ``if-else`` 语句属于行为级建模，而另外三种情况（至少对
综合工具而言）属于内建的宏处理器。因此，综合工具必须能够完全展开所有
循环，并用常量折叠求出 ``generate`` 语句中所有 ``if-else`` 语句的条件值。

数组和存储器
~~~~~~~~~~~~


Verilog 支持数组。这通常是一种可综合的语言特性。大多数情况下，数组可以
通过生成可寻址存储器来综合。然而，当使用复杂或异步的访问模式时，就无法把
数组建模为存储器。在这些情况下，必须用每个字各自独立的信号来建模数组，
并且对数组的所有访问都必须用大型多路复用器实现。

在某些情况下可以用存储器来建模数组，但并不希望这样做。考虑下面的延迟
电路：

.. code:: verilog
   :number-lines:

   module (clk, in_data, out_data);

   parameter BITS = 8;
   parameter STAGES = 4;

   input clk;
   input [BITS-1:0] in_data;
   output [BITS-1:0] out_data;
   reg [BITS-1:0] ffs [STAGES-1:0];

   integer i;
   always @(posedge clk) begin
       ffs[0] <= in_data;
       for (i = 1; i < STAGES; i = i+1)
           ffs[i] <= ffs[i-1];
   end

   assign out_data = ffs[STAGES-1];

   endmodule

这可以用一个带 STAGES 个输入端口和输出端口的可寻址存储器来实现。更好的
实现是使用简单的触发器链（即所谓的移位寄存器）。这种更好的实现可以先创建
基于存储器的实现，再根据所有端口的静态地址信号进行优化来获得，也可以直接
在语言前端识别出这类情况，并把所有存储器访问转换为对正确信号的直接访问。

数字电路综合中的挑战
--------------------


本节总结数字电路综合中最重要的挑战。工具的好坏可以用其解决这些问题的程度
来刻画。

标准符合性
~~~~~~~~~~


最重要的挑战是符合相关的 HDL 标准（对于 Verilog，是 IEEE 标准
1364.1-2002 和 1364-2005）。这可以拆分为两项：

-  标准实现的完整性
-  标准实现的正确性

完整性主要关系到保证与现有 HDL 代码的兼容性。设计一旦经过验证和测试，HDL
设计者就非常不愿意改动设计，即使只是为了绕过新综合工具中缺失的特性而做
几处小改动。

正确性至关重要。在某些方面这很明显（例如正确综合基本的行为级模型）。但
对于涉及标准细微细节的方面也同样关键，例如处理有符号表达式的确切规则，
即使 HDL 代码并不针对不同的综合工具也是如此。这是因为（与只由编译器处理
的软件源代码不同），在大多数设计流程中，HDL 代码不仅由综合工具处理，还由
一个或多个仿真器处理，有时甚至由形式化验证工具处理。让所有这些工具对 HDL
代码采用相同的解释，是这一验证过程的关键。

优化
~~~~


一般来说，很难用单一维度来描述综合工具对设计的优化效果。首先是因为并非
所有优化都适用于所有设计和所有综合任务。有些优化在粗粒度层次上（使用
加法器、乘法器等复杂单元）效果最好，另一些则在细粒度层次上（单比特门）
效果最好。有些优化针对面积，另一些针对速度。有些在大设计上效果良好，而
另一些扩展性不好，只能用于小设计。

优秀的工具能够在不同抽象层次上应用广泛的优化，并让设计者控制执行（或
跳过）哪些优化以及优化目标是什么。

工艺映射
~~~~~~~~


工艺映射是把设计转换为由目标架构中可用单元构成的网表的过程。在 ASIC
流程中，这可能是晶圆厂提供的特定工艺单元库。在 FPGA 流程中，这可能是
LUT 单元以及专用功能单元（如专用乘法器）。在粗粒度流程中，甚至可能是
更复杂的专用功能单元。

如果开源且独立于厂商的工具支持多种不同类型的目标架构，就尤其有意义。

基于脚本的综合流程
------------------


数字设计通常从实现所需功能的高级或系统级仿真开始。然后手工把这一描述转换
（或重新实现）为可综合的较低层次描述（通常处于行为级），并通过仿真两者并
比较仿真结果来验证两种表示的等价性。

之后，使用一系列工具把可综合描述转换为更低层次的表示，并再次用仿真验证
结果。这一过程如 :numref:`图 %s <fig:Basics_flow>` 所示。

.. figure:: /_images/primer/basics_flow.svg
	:class: width-helper invert-helper
	:name: fig:Basics_flow

	典型设计流程。绿色方框表示手工创建的模型。橙色方框表示由综合工具
	生成的模型。


在这个例子中，系统级模型和行为模型都是手工编写的设计文件。在验证了系统级
模型与行为模型的等价性之后，就可以使用综合工具生成设计的较低层次表示。
最后验证 RTL 模型和门级模型，设计过程即告完成。

然而，在任何真实的设计工作中，这个设计过程都会经历多次迭代。原因可能是
设计需求后期发生变更，或者对低抽象模型的分析（例如门级时序分析）表明需要
修改设计才能满足设计需求（例如尽可能高的时钟速度）。

每当行为模型或系统级模型发生变化，都必须重新运行仿真并比较结果，以重新
验证它们的等价性。每当行为模型发生变化，都必须重新运行综合，并重新验证
综合结果。

为了保证可复现性，能够用一组固定的设置轻松地重新运行设计项目中的所有自动
步骤非常重要。因此，综合流程中使用的所有程序通常都可以用脚本控制。这意味着
所有功能都可以通过文本命令使用。当这类工具提供 GUI 时，它是对命令行界面
的补充，而不是替代。

通常，UNIX/Linux 环境中的综合流程会由一个 shell 脚本控制，该脚本按正确
顺序调用所有必需的工具（本例中是综合和仿真/验证）。每个工具都会以一个
包含该工具命令的脚本文件来调用。这些脚本文件会提供工具所需的所有设置，
因此不需要人工交互。这些脚本文件被视为设计源文件，应当像系统级模型和
行为模型的源代码一样纳入版本控制。

来自编译器设计的方法
--------------------


综合工具的某些部分涉及传统上属于编译器设计的问题领域。本节讨论其中一些
领域。

词法分析和语法分析
~~~~~~~~~~~~~~~~~~


编译器设计中最知名的概念大概就是词法分析和语法分析。这两种方法结合起来
可以轻松处理复杂的计算机语言。:cite:p:`Dragonbook`

词法分析器从输入中读取单个字符，并生成由类型和值组成的词法记号流。例如，
Verilog 输入 :verilog:`assign foo = bar + 42;` 可能被词法分析器转换为
:numref:`表 %s <tab:Basics_tokens>` 中给出的词法记号列表。

.. table:: 语句 :verilog:`assign foo = bar + 42;` 的示例记号列表
	:name: tab:Basics_tokens

	============== ===============
	Token-Type     Token-Value
	============== ===============
	TOK_ASSIGN     \-
	TOK_IDENTIFIER "foo"
	TOK_EQ         \-
	TOK_IDENTIFIER "bar"
	TOK_PLUS       \-
	TOK_NUMBER     42
	TOK_SEMICOLON  \-
	============== ===============

词法分析器通常由词法分析器生成器（例如 flex）根据描述文件生成，描述文件
使用正则表达式来指定应匹配各个记号的文本模式。

词法分析器还负责跳过被忽略的字符（例如 Verilog 中字符串常量之外的空白和
注释），并把原始文本片段转换为记号值。

注意，各个关键字使用不同的记号类型（而不是使用同一种关键字类型搭配不同的
记号值）。这是因为语法分析器通常只能根据 Token-Type 来决定记号的语法角色。

随后，语法分析器把记号列表转换为语法分析树，其结构与计算机语言文法中的
产生式非常相似。与词法分析器一样，语法分析器通常也由代码生成器（例如
bison）根据巴科斯范式（BNF）写成的文法描述生成。

让我们考虑下面的 BNF（使用 Bison 语法）：

.. code:: none
   :number-lines:

   assign_stmt: TOK_ASSIGN TOK_IDENTIFIER TOK_EQ expr TOK_SEMICOLON;
   expr: TOK_IDENTIFIER | TOK_NUMBER | expr TOK_PLUS expr;

.. figure:: /_images/primer/basics_parsetree.svg
	:class: width-helper invert-helper
	:name: fig:Basics_parsetree

	Verilog 表达式
	:verilog:`assign foo = bar + 42;` 的示例语法分析树

语法分析器把记号列表转换为 :numref:`图 %s
<fig:Basics_parsetree>` 中的语法分析树。注意，语法分析树实际上从不会作为
一个完整的数据结构存在于内存中。相反，语法分析器会按深度优先顺序为语法
分析树的所有内部节点调用用户指定的代码片段（即所谓的归约函数）。

在一些非常简单的应用中（例如为栈式机器生成代码），可以直接在归约函数中
完成手头的任务。但通常归约函数只用于构建一个包含语法分析树相关信息的内存
数据结构。这种数据结构称为抽象语法树（AST）。

抽象语法树的确切格式因应用而异（而语法分析树和记号列表的格式主要由所处理
语言的文法决定）。:numref:`图 %s <fig:Basics_ast>` 展示了
:numref:`图 %s <fig:Basics_parsetree>` 中语法分析树对应的 AST 可能是什么
样子。

通常，AST 随后会被转换为另一种更适合进一步处理的表示。在编译器中，这常常
是类似汇编的三地址码中间表示。:cite:p:`Dragonbook`

多遍编译
~~~~~~~~


复杂问题通常拆分成较小的问题后解决效果最好。对编译器和综合工具来说当然
也是如此。负责解决较小问题的组件可以用两种不同方式连接：单遍流水线和
多遍处理。

传统上，语法分析器和词法分析器采用流水线方式连接：词法分析器提供一个由
语法分析器调用的函数。该函数从输入中读取数据，直到读到一个完整的词法记号。
然后把这个记号返回给语法分析器。因此词法分析器不会先生成完整的词法记号
列表再交给语法分析器。相反，它们并发运行，语法分析器可以在词法分析器产生
记号的同时消费记号。

单遍流水线方式的优点是内存占用更低（任何时候都不必把完整设计保存在内存
中），缺点是交互组件之间的耦合更紧。

因此，只在需要较低内存占用，或者组件在概念上也紧密耦合时，才应使用单遍
流水线。后者对于语法分析器及其词法分析器来说确实如此。但当数据在两个概念
上松散耦合的组件之间传递时，通常使用多遍方式更有利。

在多遍方式中，第一个组件处理所有数据，结果保存在内存数据结构中。然后用
这些数据调用第二个组件。这降低了复杂度，因为同一时间只有一个组件在运行。
它还提高了灵活性，因为组件可以更容易地替换。

大多数现代编译器都是多遍编译器。

静态单赋值（SSA）形式
~~~~~~~~~~~~~~~~~~~~~


在命令式编程（以及行为级 HDL 设计）中，同一个变量可以被多次赋值。这可能
意味着该变量在两个不同上下文中被独立使用，或者该变量的最终值取决于某个
条件。

下面的示例展示的 C 代码中，一个变量在两个不同上下文中被独立使用：

.. code:: c++
   :number-lines:

   void demo1()
   {
       int a = 1;
       printf("%d\n", a);

       a = 2;
       printf("%d\n", a);
   }

.. code:: c++

   void demo1()
   {
       int a = 1;
       printf("%d\n", a);

       int b = 2;
       printf("%d\n", b);
   }

.. code:: c++
   :number-lines:

   void demo2(bool foo)
   {
       int a;
       if (foo) {
           a = 23;
           printf("%d\n", a);
       } else {
           a = 42;
           printf("%d\n", a);
       }
   }

.. code:: c++

   void demo2(bool foo)
   {
       int a, b;
       if (foo) {
           a = 23;
           printf("%d\n", a);
       } else {
           b = 42;
           printf("%d\n", b);
       }
   }

在两个示例中，左侧版本（只有变量 ``a``）和右侧版本（变量 ``a`` 和
``b``）是等价的。因此，为了进一步处理，希望把代码转换为两种情况下都等价
的统一形式。

在下面的示例中，该变量被赋值两次，但不能轻易地用两个变量替换：

.. code:: c++

   void demo3(bool foo)
   {
       int a = 23
       if (foo)
           a = 42;
       printf("%d\n", a);
   }

静态单赋值（SSA）形式是一种命令式代码表示，它对示例 1 和示例 2 的左右
两个版本使用相同的表示，但仍能表示示例 3。在 SSA 形式中，每次赋值都赋给
一个新变量（通常带索引书写）。但它还引入了特殊的 :math:`\Phi` 函数，在
需要时合并变量的不同实例。用 C 伪代码书写时，示例 3 使用 SSA 形式如下：

.. code:: c++

   void demo3(bool foo)
   {
       int a_1, a_2, a_3;
       a_1 = 23
       if (foo)
           a_2 = 42;
       a_3 = phi(a_1, a_2);
       printf("%d\n", a_3);
   }

在代码生成过程中，:math:`\Phi` 函数通常被解释为“这些变量必须存储在同一个
内存位置”。大多数针对 C/C++ 等命令式语言的现代编译器至少在某些 pass 中
使用 SSA 形式，因为它非常容易操作和分析。

.. [1]
   近年来，形式化等价检查也成为一种重要的验证方法，用于验证设计的 RTL
   表示和更低抽象层次的表示。
